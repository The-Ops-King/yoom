## Goal

Tyler, after the first launch (2026-09-02):

> "I want it to be like Loom and have the app basically disappear except for basic functionality, then be able to move the camera bubble around."
> "it never asked for my microphone settings, and won't let me select."
> "we'll absolutely need to update the UI to make it accessible, and a tiny overlay app like loom."

Three deliverables:

1. **Permissions actually get asked for.** On `app.whenReady()` the shell calls `systemPreferences.askForMediaAccess('microphone')` and `('camera')`, and surfaces the Screen Recording deep link when that status is not `granted`. The web-side `DeviceSelector` re-enumerates once the grant lands, so the microphone picker stops being empty.
2. **A recording HUD.** A ~320×56 always-on-top, frameless, transparent-cornered, draggable pill: REC dot + elapsed timer, Pause/Resume, Stop, Cancel, Mark, camera-bubble toggle. It appears for `countdown`/`recording`/`paused`/`stopping` and hides otherwise.
3. **The main window disappears while recording.** Entering `countdown` hides the recorder window (it stays alive — the encoder, the compositor and the `beforeunload` guard all live in that renderer); entering `review`/`error`/`idle` shows and focuses it again. The countdown itself is rendered by the HUD, because the page that used to render it is no longer on screen.
4. **The camera light goes out.** Tyler again: *"Terminal has access to my camera and won't shut it off."* The bubble renderer held its `getUserMedia` track for the life of a window that was hidden but never destroyed. Task 5 releases the track on every hide path and destroys the window when the take is over.

**Non-goals:** a separate always-running "launcher" window, HUD-driven device switching, HUD-driven mode switching, drag-to-reposition persistence across relaunches, Windows/Linux, code signing. The bubble's control strip is deliberately left alone — the HUD owns transport controls, the bubble stays a clean camera preview.

```
┌─ desktop/ ──────────────────────────────────────────────────────────────────┐
│  main                                                                       │
│    index.ts        + askForMediaAccess on ready, + installHudIpc/destroyHud  │
│    hud.ts     NEW   HUD BrowserWindow, HudState store, recorder show/hide,   │
│                     content protection, idle auto-hide escape hatch          │
│    windows.ts      + hideRecorderWindow / showRecorderWindow                 │
│    tray.ts         + recording-aware items, permission statuses, dev tools   │
│    mapping.ts      + hudDefaultBounds (PURE), recorderWindowVisibility (PURE)│
│                                                                             │
│  preload/hud.ts + hud.channels.ts   NEW → window.__yoomHud                   │
│  preload/app.channels.ts            + setHudState                            │
│  renderer/hud/{index.html,hud.css,hud.ts}  NEW                               │
└─────────────────────────────────────────────────────────────────────────────┘

  web → main            main → HUD renderer        HUD renderer → main
  ──────────────────    ────────────────────       ───────────────────
  yoom:hud-state        yoom:hud:apply             yoom:hud:action
  (HudState, ~4 Hz)     (HudState, on change)      (DesktopShortcut)
                                                   yoom:hud:interact

  main → web renderer: yoom:shortcut (existing channel, now also carries
                       'bubbleToggle')
```

**Why the HUD gets its state from the web app rather than counting itself.** The elapsed timer, the pause offsets, the marker count and the max-duration cut-off all live in `recorder-machine.ts`. A second clock in the main process would drift against the one burned into the recording. So the page stays authoritative and pushes `HudState` at ~4 Hz; the HUD is a dumb view.

**Why hide-not-close for the recorder window.** `MediaRecorder`, the compositor RAF loop and the `beforeunload` guard all live in that renderer. `win.hide()` keeps the renderer running (the window already sets `backgroundThrottling: false`, which is what makes a hidden window keep compositing at full rate). Closing it would destroy the take.

**Self-occlusion and the HUD.** Unlike the bubble, the HUD has no composited twin drawn over it, so `setContentProtection(true)` is the only defence — and on macOS ≥ 14 ScreenCaptureKit-based capturers (Chromium's included) capture the window anyway. Decision: apply it best-effort, default the HUD to the **top-centre of the work area** (out of the way of most content, and the first place a viewer's eye forgives a control bar), document that it may appear in full-screen recordings, and ship `YOOM_HUD_HIDE_WHILE_RECORDING=1`, which hides the HUD 1 s after the last interaction and brings it back on any hotkey, action or status change. This mirrors Loom: its control bar is also captured unless you drag it off-screen.

## Tech Stack

No new dependencies. Everything below uses APIs already in `electron@44.1.1`:

| API | Where | Why |
|---|---|---|
| `systemPreferences.askForMediaAccess('microphone' \| 'camera')` | `permissions.ts` (exists) | The only way to raise the macOS mic/camera prompt from code. Returns a Promise<boolean>. |
| `systemPreferences.getMediaAccessStatus('screen')` | `permissions.ts` (exists) | Screen Recording cannot be prompted; only read and deep-linked. |
| `BrowserWindow` `transparent` + `frame:false` + `setAlwaysOnTop(true,'floating')` | `hud.ts` | Same recipe the bubble already uses. |
| `win.setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true })` | `hud.ts` | The HUD must survive a Space switch mid-recording. |
| `win.setContentProtection(true)` | `hud.ts` | Best-effort exclusion; see Architecture. |
| `-webkit-app-region: drag` | `hud.css` | Makes the pill draggable; buttons opt out with `no-drag`. |
| `screen.getPrimaryDisplay().workArea` | `hud.ts` | Top-centre placement must clear the menu bar, so `workArea`, not `bounds`. |
| `webContents.openDevTools({ mode: 'detach' })` | `tray.ts` | Dev ergonomics — the recorder window has no menu bar to open them from. |

The bug: `DeviceSelector` calls `warmPermissions` once on mount. In the shell, that `getUserMedia` fires before macOS has granted anything, so it rejects, `enumerateDevices` returns unlabelled-or-empty, and nothing ever retries. Task 11 makes the shell prompt at launch — this task makes the page notice.

**Files:** `src/components/device-selector.tsx`, `src/components/recorder.tsx`

- [ ] Replace the whole `useEffect` in `src/components/device-selector.tsx` with:

```ts
  useEffect(() => {
    let cancelled = false;
    const provider = getProvider();

    /**
     * `warmPermissions` is a `getUserMedia` call whose only purpose is to make
     * macOS/Chromium hand back device *labels*. In the desktop shell it can
     * legitimately fail the first time — the TCC prompt may still be on screen
     * — so an empty list is a reason to warm again, not a permanent answer.
     */
    async function load(warm: boolean): Promise<void> {
      if (warm) await provider.warmPermissions(kind);
      const filtered = await provider.enumerateDevices(kind);
      if (cancelled) return;
      setDevices(filtered);
      if (filtered.length > 0 && !value) onChange(filtered[0].deviceId);
      if (value && !filtered.some((device) => device.deviceId === value)) onChange("");
    }

    void load(true);

    const md = typeof navigator !== "undefined" ? navigator.mediaDevices : null;
    // A grant landing (or a device being plugged in) fires `devicechange`.
    // Re-warm when we still have nothing: the grant that just landed is
    // exactly the case where the first warm failed.
    const onDeviceChange = () => {
      void load(devicesRef.current.length === 0);
    };
    md?.addEventListener?.("devicechange", onDeviceChange);

    return () => {
      cancelled = true;
      md?.removeEventListener?.("devicechange", onDeviceChange);
    };
    // `value`/`onChange` are intentionally excluded: re-running on every
    // selection would re-prompt for permissions.
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [kind]);
```

## Task 5

Camera hygiene. Tyler, 2026-09-02: *"Terminal has access to my camera and won't shut it off."*

**The bug.** The bubble renderer calls `getUserMedia` once and only ever stops the tracks on `pagehide`. `bubble.ts#sync()` hides the window but never destroys it, and the window is never destroyed until quit — so a hidden bubble window is still holding an open camera track and the macOS camera indicator stays lit for the whole session, long after the recording ended. Three layers of fix: release on hide, destroy the window when the take is well and truly over, and tear both windows down on quit.

```ts
/**
 * The HUD window's size in device-independent pixels. The pill itself is
 * 320×48; the window is larger so the drop shadow and the transparent rounded
 * corners have room, since a transparent window cannot paint outside itself.
 */
export const HUD_SIZE = { width: 336, height: 64 } as const;

/** Gap between the top of the work area and the top of the HUD window. */
export const HUD_TOP_INSET = 12;

/**
 * Default HUD placement: horizontally centred at the top of the WORK AREA.
 *
 * `workArea`, not `bounds` — `bounds` starts behind the menu bar, and a pill
 * tucked under the menu bar cannot be dragged. Top-centre is deliberate: it is
 * the least destructive place for a bar that macOS ≥ 14 will capture anyway
 * (see `hud.ts`), and it is where Loom parks its control bar's neighbours.
 */
export function hudDefaultBounds(workArea: Bounds): Bounds {
  const width = HUD_SIZE.width;
  const height = HUD_SIZE.height;
  // A display that has gone away mid-session reports non-finite bounds; treat
  // it as a zero-sized area at the origin rather than producing NaN bounds.
  const areaX = Number.isFinite(workArea.x) ? workArea.x : 0;
  const areaY = Number.isFinite(workArea.y) ? workArea.y : 0;
  const areaW = Number.isFinite(workArea.width) ? workArea.width : 0;
  return {
    x: Math.round(areaX + Math.max(0, (areaW - width) / 2)),
    y: Math.round(areaY + HUD_TOP_INSET),
    width,
    height,
  };
}

/** Statuses during which the recorder window is deliberately off screen. */
const HIDDEN_DURING: ReadonlySet<HudStatus> = new Set([
  "countdown",
  "recording",
  "paused",
  "stopping",
]);

/** Statuses that end a take and must bring the recorder window back. */
const RESTORES: ReadonlySet<HudStatus> = new Set(["review", "error", "idle"]);

export type RecorderVisibility = "hide" | "show" | "none";

/**
 * What to do with the recorder window on a status transition.
 *
 * Loom-style "the app disappears": entering `countdown` hides it, and only a
 * transition OUT of a hidden status INTO a resolving one brings it back. The
 * `prev` guard is what stops an `idle → review` transition (which never hid
 * anything) from yanking a window the user had deliberately hidden themselves.
 */
export function recorderWindowVisibility(
  prev: HudStatus,
  next: HudStatus,
): RecorderVisibility {
  if (prev === next) return "none";
  if (next === "countdown") return "hide";
  if (HIDDEN_DURING.has(prev) && RESTORES.has(next)) return "show";
  return "none";
}
```

```ts
  if (!VISIBLE_DURING.has(state.status)) return;
  const win = alive();
  if (win && !win.isVisible()) win.showInactive();
  armAutoHide(AUTO_HIDE_DELAY_MS);

  if (!AUTO_HIDE) return;
  if (!VISIBLE_DURING.has(state.status)) return;
  alive()?.showInactive();
  armAutoHide(AUTO_HIDE_WAKE_MS);
}

/** Tray "Show controls" / "Hide controls". */
export function toggleHud(): void {
  const win = alive();
  if (!win) {
    if (VISIBLE_DURING.has(state.status)) sync();
    return;
  }
  if (win.isVisible()) {
    clearAutoHide();
    win.hide();
  } else {
    win.showInactive();
    armAutoHide(AUTO_HIDE_WAKE_MS);
  }
}

function sync(): void {
  if (!VISIBLE_DURING.has(state.status)) {
    clearAutoHide();
    alive()?.hide();
    return;
  }
  const win = createHudWindow();
  win.webContents.send(IPC.hudApply, state);
  // Showing before the renderer has painted flashes an unstyled transparent
  // frame; `onLoaded` shows it itself once the first paint lands.
  if (hudLoaded && !win.isVisible()) win.showInactive();
}

/**
 * Untrusted input: the payload comes from a renderer. A bad status would put
 * the pill in a state no branch handles, and a NaN elapsed would render "NaN".
 */
function parseHudState(value: unknown): HudState | null {
  if (!value || typeof value !== "object") return null;
  const raw = value as Record<string, unknown>;
  const status = raw.status as HudStatus;
  if (!STATUSES.includes(status)) return null;
  const num = (v: unknown): number =>
    typeof v === "number" && Number.isFinite(v) && v >= 0 ? v : 0;
  return {
    status,
    elapsedMs: num(raw.elapsedMs),
    countdown: num(raw.countdown),
    markers: Math.round(num(raw.markers)),
    bubbleVisible: !!raw.bubbleVisible,
  };
}

export function setHudState(next: HudState): void {
  const prev = state.status;
  const statusChanged = prev !== next.status;
  state = next;

  if (statusChanged) {
    // Loom-style disappearing act, decided by a pure function so it is
    // testable: see mapping.ts#recorderWindowVisibility.
    const action = recorderWindowVisibility(prev, next.status);
    if (action === "hide") hideRecorderWindow();
    else if (action === "show") showRecorderWindow();
  }

  sync();

  if (statusChanged) {
    wakeHud();
    onStatusChange?.();
  }
}

export function destroyHud(): void {
  clearAutoHide();
  alive()?.destroy();
  hudWindow = null;
  hudLoaded = false;
  state = INITIAL;
}

  "toggle",
  "pause",
  "mark",
  "restart",
  "cancel",
  "bubbleToggle",
];

    const parsed = parseHudState(next);
    if (!parsed) return;
    setHudState(parsed);
  });

  ipcMain.on(IPC.hudAction, (_e, action: unknown) => {
    if (!ACTIONS.includes(action as DesktopShortcut)) return;

    // global hotkeys are the same remote-control actions, and the web app
    // already owns every status guard for them.
    sendToRecorder(IPC.shortcut, action as DesktopShortcut);
    noteHudInteraction();
  });

  ipcMain.on(IPC.hudInteract, () => noteHudInteraction());
}
```

```ts
  if (process.platform !== "darwin") {

  }
  return {

    camera: systemPreferences.getMediaAccessStatus("camera"),
    microphone: systemPreferences.getMediaAccessStatus("microphone"),
  };

/**
 * Run once at launch. `askForMediaAccess` raises the macOS prompt the FIRST
 * time it is called for a given binary and resolves immediately with the
 * remembered answer afterwards, so this is cheap on every subsequent launch.
 *
 * Doing it here rather than lazily is the whole point: the web app's device
 * pickers enumerate on mount, and before a grant `enumerateDevices` returns
 * nothing usable — which is exactly the empty microphone list from the first
 * launch. `DeviceSelector` re-enumerates on the `devicechange` that a grant
 * fires, so the two halves meet.
 *
 * Screen Recording CANNOT be prompted from code — macOS raises it on the first
 * real capture and requires a relaunch — so it is only reported, with a deep
 * link into the right pane.
 */
export async function warmPermissionsAtLaunch(): Promise<void> {
  if (process.platform !== "darwin") return;
  try {
    await requestMediaAccess();
  } catch (err) {
    // A denial is a resolved `false`, not a throw; this is for the genuinely
    // unexpected, and must never take the launch down with it.
    console.warn("[yoom] askForMediaAccess failed", err);
  }

  if (hasScreenAccess()) return;

  const { response } = await dialog.showMessageBox({
    type: "info",
    title: "Yoom needs Screen Recording access",
    message: "Screen Recording is not granted yet",
    detail: [
      "macOS cannot be asked for Screen Recording from inside an app. Grant",
      "Yoom under Privacy & Security → Screen Recording, then quit and",
      "relaunch Yoom — the grant does not take effect until you do.",
      "",
      "Camera and Microphone have been requested already; answer their prompts",
      "if they are still on screen.",
    ].join("\n"),
    buttons: ["Open System Settings", "Later"],
    defaultId: 0,
    cancelId: 1,
  });
  if (response === 0) openPrivacyPane("screen");
}
```

```md
Entering the 3-2-1 countdown **hides** the recorder window (it is not closed —
the encoder, the compositor and the unsaved-work guard all live in that
renderer) and puts a 320×48 pill at the top centre of the screen:

| Control | Action | Hotkey |
|---|---|---|
| ⏸ / ▶ | Pause / resume | ⌘⇧P |
| ■ | Stop and go to review | ⌘⇧L |
| ⚑ | Drop a marker | ⌘⇧M |
| ◉ | Show/hide the camera bubble | — |
| 🗑 | Discard the take | ⌘⇧X |

Drag the pill anywhere by its body. The recorder window comes back — shown and
focused — as soon as the take reaches review, error or idle. The tray mirrors
the same controls, and ⌘⇧L works throughout.

**The HUD will appear in a full-screen recording.** `setContentProtection(true)`
is applied, but macOS ≥ 14's ScreenCaptureKit — which Chromium uses — ignores
it, exactly as it does for the bubble. Unlike the bubble, the HUD has no
composited twin drawn over it to hide it. Two answers:

- Drag the pill onto a second display, or onto the part of the screen you are
  not capturing. This is what Loom users do with Loom's control bar, which has
  the same limitation.
- Run with `YOOM_HUD_HIDE_WHILE_RECORDING=1`. The pill hides itself 1 s after
  your last interaction with it and reappears for 2 s whenever a hotkey fires,
  the status changes, or you use the tray's "Show/hide controls".

## Debugging

There is no menu bar (`LSUIElement: true`), so the usual View → Toggle
Developer Tools is not there.

- **Recorder window DevTools:** tray → Developer → Developer tools. Opens
  detached, so it does not resize the page mid-recording.
- **Hard reload the web app:** tray → Developer → Reload recorder
  (`reloadIgnoringCache`). Use it after a deploy rather than restarting the shell.
- **HUD / bubble / picker renderers:** they have no menu either. In dev they are
  served by electron-vite, so the quickest path is `console.log` plus the
  terminal running `npm run dev`, which carries renderer console output. To
  attach real DevTools, temporarily add `win.webContents.openDevTools({ mode: "detach" })`
  next to the window's `loadURL`/`loadFile` call.
- **Main-process logs:** the terminal running `npm run dev`. In a packaged
  build, launch from a terminal — `/Applications/Yoom.app/Contents/MacOS/Yoom` —
  to see them.
- **IPC not arriving?** Check `desktop/src/preload/channels.test.ts` first
  (`npm --prefix desktop test`). A preload silently missing its bridge is
  almost always a channel-string drift or a sandbox chunking regression — see
  the header comment in `app.channels.ts`.
- **Permissions:** tray → Permissions… shows all three statuses and offers the
  deep links. Remember that an unsigned rebuild is a new app to macOS TCC.
- **"Terminal has access to my camera":** under `npm run dev` macOS attributes
  camera and microphone use to the **launching process** — your terminal —
  because the running binary is `node_modules/electron/dist/Electron.app` and
  the privacy indicator follows the responsible process. The packaged app shows
  up as "Yoom". So the scary Terminal entry in Control Centre is a dev-only
  artefact of *who launched it*, not of *what is holding the device*. To check
  whether the camera is genuinely still open, watch the green LED / menu-bar
  dot: it should go out within ~2 s of a take reaching review (see "Camera
  release" below).

## Camera release

The floating bubble is a second, independent `getUserMedia` in its own
renderer. Hiding that window does **not** stop its tracks, so the shell sends
the renderer an explicit release on every hide path — it stops every track and
clears `srcObject` — and destroys the window entirely if it stays unwanted for
2 s. Recreating it is cheap. `before-quit` destroys it while it still exists,
so the indicator goes out when you quit rather than when the process exits.

The recorder page's *own* camera is separate and stays live through
`review → setup` on purpose: you are about to shoot another take, and
re-acquiring would re-prompt and re-flash the camera. Loom behaves the same
way. It is released by `teardown()` on upload, reset, idle and error.
```

## Self-review

**Where this could go wrong, and why it does not.**

1. **The hidden recorder window stops compositing.** It would, if `backgroundThrottling` were on — it is explicitly `false` in `createRecorderWindow` (Phase 4 set it for exactly this class of problem). A hidden window with throttling off keeps its RAF loop at full rate. *Verified by matrix B: the finished recording must be smooth end to end, not just at the start.*

2. **Two clocks disagree.** There is only one clock: `recorder-machine.ts`. The HUD renders what it is handed. The `formatElapsed` duplication in `hud.ts` is the only overlap, and it is a copy of eight lines with a comment saying so.

3. **The 250 ms push is a performance problem.** It carries a five-field plain object across the contextBridge four times a second, and only while counting down or recording. The bubble's drag path already pushes more than that.

4. **`bubbleToggle` desyncs the two bubbles.** It dispatches `SET_BUBBLE { visible }`, which flows through the existing appearance effect back to `bubble.ts`. The web state stays authoritative, exactly as the bubble's own hide button already works.

5. **A malicious/garbled renderer payload.** `parseHudState` validates the status against a literal list and coerces every number, mirroring `parseAppearance`. `hudAction` validates against the `DesktopShortcut` list before forwarding. Neither can produce NaN bounds or an unhandled state.

6. **The HUD is stranded on screen after a crash in the page.** `window-all-closed` and `will-quit` both call `destroyHud()`. If the renderer wedges without closing, the tray's "Show/hide controls" and Quit both still work — the pill is a separate process from the page.

7. **`recorderWindowVisibility` yanks a window the user hid themselves.** Guarded: the `show` branch requires the *previous* status to be one during which the shell itself hid the window.

8. **Destroying the bubble window mid-take.** `scheduleRelease` re-checks `shouldShow()` inside the timer before destroying, and `sync()` cancels the timer on every show. The 2 s debounce exists precisely so `recording → stopping → review` cannot destroy-and-recreate across a transient hidden state — and the window-capture / framed-capture auto-hide, which hides the bubble *during* a take, will release the camera and destroy the window; that is correct, because the bubble is not on screen and the burned-in bubble comes from the page's own camera, not this one.

9. **The bubble's camera does not come back after a release.** `release()` clears `openingFor`, so the next `bubbleCamera` for the same device is not short-circuited by the "already open" guard — and `sync()` sends `bubbleCamera` on every show. A release that forgot to clear `openingFor` would leave a permanently black bubble; that is the single most likely regression in Task 5 and the reason the guard is reset explicitly rather than incidentally.

10. **A sandboxed preload silently loses its bridge.** The mechanism that would cause it (a shared Rollup chunk) is fenced by `hud.channels.ts` plus the extended `channels.test.ts`, and Task 15 greps the built bundle for `chunks/`.

**Deliberate omissions, and why.**

- **No global accelerator for `bubbleToggle`.** Five chords are already registered and each one is a chance to collide with another app. The HUD button is always on screen during a take, which is the only time the action means anything.
- **No Pause/Stop on the camera bubble.** Tyler's ask was for the bubble to be draggable and clean. Two places to stop a recording is two places to get the state wrong; the HUD owns transport.
- **HUD position is not persisted.** Persisting it means deciding what to do when the display it was on is gone. Top-centre of the primary display every time is predictable, and the drag is one gesture.
- **No `restart` button on the pill.** Six controls in 320 px is already tight, and ⌘⇧K still works globally. The HUD is the *basic functionality* Tyler asked for, not the full toolbar.
